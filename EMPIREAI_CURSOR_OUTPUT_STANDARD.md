# EmpireAI — Cursor Output Standard

> **Canonical label:** Cursor Output Standard  
> **Canonical owner:** Repository Governance · Pillow Architecture · Cursor  
> **Authority:** Grand King Workflow Decision · EmpireAI Version 1 · **Parent law:** [`EMPIREAI_CONSTITUTION.md`](./EMPIREAI_CONSTITUTION.md) (Engineering Constitution · P2-03 §8)
> **Status:** ✅ Permanent workflow standard  
> **Registered:** 2026-06-29  
> **Companion artifacts:** `EMPIREAI_EXECUTIVE_AUDIT_STANDARD.md` · `docs/governance/CURSOR_OUTPUT_TEMPLATE.md` · `PILLOW_ARCHITECTURE_CONTRACT.md` §4.8 · **`EMPIREAI_CONTINUOUS_ARTIFACT_GENERATION_WORKFLOW.md`**

Every **Cursor Output** (artifact type: **Mission Specification**) generated by ChatGPT, Pillow Mission Planner, or any EmpireAI advisor **shall** follow this two-section format before Grand King approval or Cursor handoff.

**Parent workflow:** Mission Specifications are one artifact type within the **Continuous Artifact Generation Workflow** — conversation is not the final output; lasting decisions produce repository artifacts.

---

## 1. Purpose

Upgrade EmpireAI workflow so every repository artifact preserves **both**:

1. **Executive intent** — why the work exists and what Grand King should verify  
2. **Engineering implementation** — complete specification for Cursor  

Grand King verifies understanding **before** approving implementation. Cursor receives **only** the engineering specification.

---

## 2. Constitutional principle

**Every lasting EmpireAI decision shall preserve both executive intent and engineering implementation.**

No implementation shall exist without preserving the reasoning that justified it.

This principle aligns with:

* GVD-019 — Grand King approval before irreversible action  
* `EMPIREAI_REPOSITORY_FIRST_DOCTRINE.md` — repository is permanent memory  
* `EMPIREAI_PILLOW_EXECUTIVE_INTELLIGENCE_CONSTITUTION.md` §3 — conversation → candidate knowledge → approval → knowledge base  
* **`EMPIREAI_CONTINUOUS_ARTIFACT_GENERATION_WORKFLOW.md`** — default workflow; conversation is not the final output  

---

## 3. Mandatory structure

Every Cursor Output **shall** contain exactly **two sections** in this order:

```
SECTION 1 — Executive Summary   (Grand King audience)
SECTION 2 — Cursor Draft        (Cursor engineering audience)
```

Use the headings **`## SECTION 1 — Executive Summary`** and **`## SECTION 2 — Cursor Draft`** (or equivalent level-2 markers) so parsers and reviewers can distinguish sections reliably.

---

## 4. SECTION 1 — Executive Summary

### Purpose

Allow Grand King to verify understanding **before** approving implementation.

### Audience

**Grand King only.** This section is **never** interpreted as implementation instructions.

### Required fields

Every Executive Summary **shall** include these subsections (exact headings recommended):

| Field | Requirement |
|---|---|
| **My Understanding** | Plain-language restatement of what Pillow/ChatGPT believes Grand King is asking for |
| **Why this recommendation exists** | Repository evidence, blockers, or strategic rationale — not chat history alone |
| **Expected Outcome** | What success looks like after implementation closes |
| **Repository Impact** | Which canonical owners, artifacts, or runtime surfaces will change |
| **Risk Assessment** | What could go wrong; dependencies; irreversible actions; governance gaps |
| **Recommendation** | Approve · Defer · Revise · Reject — with one-sentence justification |

### Rules

* Write for executive verification, not engineering detail.  
* Cite repository artifacts where possible (`JOURNEY.md`, contracts, ADRs).  
* Do **not** embed file paths, code snippets, or step-by-step implementation unless needed for impact clarity.  
* Grand King reads Section 1; Cursor **shall not** treat Section 1 as executable scope.

---

## 5. SECTION 2 — Cursor Draft

### Purpose

Provide the **complete implementation specification** for Cursor.

### Audience

**Cursor engineering worker only.** This is the sole section intended for implementation.

### Required content (minimum)

Section 2 **shall** include all items needed for Cursor to execute without inferring executive intent from conversation:

| Block | Requirement |
|---|---|
| Mission ID and title | e.g. `PILLOW-017`, `UX-014` |
| Mission type | Engineering Operations · UX · Governance · etc. |
| Authority | Contract, ADR, or doctrine citation |
| Objective | Scoped deliverable |
| Dependencies | Verification checklist with evidence |
| Implementation rules | Constraints, prohibitions, read-only rules |
| Acceptance criteria | Verifiable closeout conditions |
| Validation | typecheck, build, tests, audits |
| Executive Audit expectations | Closeout sections per `EMPIREAI_EXECUTIVE_AUDIT_STANDARD.md` |
| Stop rule | When Cursor stops |

Legacy single-section mission documents (pre-2026-06-29) remain valid historical artifacts. **New** outputs shall use the two-section format.

---

## 6. Workflow

```
Repository state / Grand King request
        ↓
Advisor (Pillow / ChatGPT) drafts Cursor Output
        ↓
SECTION 1 — Executive Summary  →  Grand King review
        ↓
Grand King approval (Approval Gate · GVD-019)
        ↓
SECTION 2 — Cursor Draft  →  Cursor Bridge handoff
        ↓
Implementation + Executive Audit (references Section 1)
        ↓
Repository artifacts updated (Journey · Audit · owners)
```

| Stage | Section used |
|---|---|
| Pillow chat preview | Both — Summary shown first for GK |
| Approval Gate proposal | Section 1 attached as rationale; Section 2 as payload |
| Cursor handoff | **Section 2 only** as primary implementation authority |
| Executive Audit closeout | **Section 1** referenced for intent traceability |

---

## 7. Traceability (Executive Audits)

Executive Audits **shall** reference the **Executive Summary** (Section 1) of the originating Cursor Output when explaining:

| Audit question | Section 1 field |
|---|---|
| Why does this artifact exist? | Why this recommendation exists |
| What decision created it? | My Understanding · Recommendation |
| What outcome was expected? | Expected Outcome |
| Does implementation match original intent? | Compare closeout to Expected Outcome + Repository Impact |

See `EMPIREAI_EXECUTIVE_AUDIT_STANDARD.md` §6 (Cursor Output traceability).

Pillow Mission Planner (`pillow/src/planner/generator.ts`) emits this format automatically for generated missions.

---

## 8. Prohibitions

Cursor Outputs shall **never**:

* Omit Section 1 when Grand King approval is required  
* Place implementation-only instructions solely in Section 1 without Section 2  
* Auto-dispatch Section 2 to Cursor without Approval Gate when repository writes are involved  
* Discard Executive Summary after implementation — it remains part of the mission artifact
