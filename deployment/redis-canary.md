# Disposable Redis expiry supervisor

Recovery3's application expiry was 14:51 UTC, but its unsupervised Redis image was manually stopped at 14:58:48 UTC. That late-stop failure remains evidence; these new files do not retroactively fix it.

This image is for a NEW isolated engineering Redis service only. Do not apply it to production. It uses Redis 7.2.16-bookworm, with Node 22.23.2 copied from the matching Debian base for the existing process-group supervisor. `libstdc++6` and `libatomic1` are explicitly installed; image build executes both binaries and rejects version mismatch. No local Docker/image execution has yet been proven.

`deployment/railway.redis-canary.toml` is a reference contract, not proof that Railway applies it. The inspected Railway UI says new services that never used Config-as-Code cannot opt in after 2026-08-28. Set and independently read back the Dockerfile builder/path, absent start-command override, restart policy NEVER, one replica, private networking only, dedicated `/data` volume and provider resource limits through the actual service UI/API before launch. The script cannot delete resources; retained volume billing still requires cleanup.

Required nonsecret configuration: engineering mode true; disposable acknowledgement; `EMPIRE_CANARY_EXPIRES_AT` as fixed UTC ISO with milliseconds, at most one hour away and at least 20 seconds of shutdown grace; provider project/environment/service IDs confirmed independently by `EMPIRE_CANARY_PROJECT_ID`, `EMPIRE_CANARY_ENVIRONMENT_ID`, `EMPIRE_CANARY_REDIS_SERVICE_ID`; environment label; actual deployment UUID and source commit. Known production identities are rejected. An isolated project's default label may be "production": exact IDs carry authority, labels do not. Use the SAME expiry as the paired application; never calculate a fresh relative expiry during redeploy.

Provide only a freshly generated disposable `REDIS_PASSWORD` of 48–128 lowercase hex characters. Password goes into a mode-0600 config file; it is excluded from child arguments/environment and lifecycle logs. Other credential-shaped environment fields cause refusal. Never use production account credentials. `/data/canary-redis/expiry-scope.json` is write-once and binds project/environment/service/source/expiry. A changed binding, malformed record, symlink or hardlink is rejected without replacing the marker. Directory must remain controlled by trusted deployment processes, not concurrently writable by hostile actors.

At expiry minus 20 seconds, the supervisor signals Redis with SIGTERM, allowing Redis's normal AOF shutdown. At the fixed expiry it kills any remaining process group and exits unsuccessfully if shutdown was forced/failed. External SIGTERM follows the same bounded path. Original marker prevents renewed time on restart. The official entrypoint drops the child to the Redis user; it retains the base image's behavior rather than reimplementing AOF shutdown. A successful process exit alone does not prove AOF data recovery.

Logs include searchable `message` fields and explicit forced-termination facts. Actual provider retrieval, same-image AOF restart/integrity and signal behavior require Linux CI/image and subsequent authorized hosted evidence. A clock/CPU scheduling pause, provider interruption, or SIGKILL can prevent an orderly flush; do not label those zero-loss. No Birth, commerce or model-spend authority is granted.

Offline command: `node --test deployment/redis-canary-launcher.test.cjs`. Windows proves configuration/marker/secret contracts and rejects unsupported process supervision; Linux additionally runs real child deadline and external-signal cases. The probe is unchanged. A separately reviewed shared-supervisor change now emits its stop receipt promptly when the child has exited and its process group is confirmed absent; remaining descendants still receive bounded cleanup.

Local validation: first Windows run had one fixed-config-path assertion failure because a platform path join produced backslashes; the fixed Linux path contract was made platform-independent. Subsequent run passed 7/7 with zero skips, and independent review reran 7/7 successfully. Those seven Windows cases do not include Linux signal/AOF/container execution. No local Docker executable was available; do not treat source configuration tests as an image build or hosted expiry receipt.

Upstream image/entrypoint references: https://github.com/redis/docker-library-redis/blob/master/7.2/debian/Dockerfile and https://github.com/redis/docker-library-redis/blob/master/docker-entrypoint.sh . These explain the base image's Redis-user transition; they are not proof this new image has built or run.

It builds the actual image and runs `deployment/redis-canary-image.test.cjs` with fresh disposable credentials and temporary Docker resources only. The test requires authenticated Redis/AOF configuration, clean external SIGTERM, rejected persisted-expiry renewal, AOF reopen, supervisor/Redis exit before the original fixed deadline, and verified cleanup. Its roughly 65-second runtime excludes image build time. No Linux image receipt exists until this job actually runs; this does not prove provider log retrieval, provider cleanup, power-loss recovery or hosted readiness.
