# CJ receipt integrity repair — bounded engineering evidence

Source baseline: `72d08d189fda37869d1f037f8b37e8be8240257a`.

This change removes misleading success paths. It does not authorize, demonstrate, or certify live dropshipping. Canonical state stays `NOT_BORN`, real commerce unauthorized, and Wave credit unchanged.

## Behavior corrected

- Missing LIVE credentials no longer silently become mock/sandbox orders. Mock fulfillment must be explicit and is rejected on production/Railway deployments.
- The public submit/tracking service reads the canonical operating projection before provider access. Enabled flags, APPROVED records, and token-shaped fields cannot override locked commerce authority.
- A legacy LIVE client with no reliable receipt/reconciliation ledger is blocked. Its readiness helper also returns false for LIVE.
- Provider order creation accepts a nonempty provider order ID only. A successful create without tracking leaves tracking unknown. No synthetic LIVE ID or tracking is manufactured.
- Order shape, approval fields, and order validity are checked before the public service can call a provider. The provider adapter disables automatic retries of create requests.
- Lost or malformed acknowledgements become `SUBMISSION_UNKNOWN`. Retry, reapproval, and reprepare cannot bypass that state. A local failure after acknowledgement also remains uncertain and retains a known provider ID for reconciliation.
- Tracking requires matching tracking identification, carrier, supported status, and source scan timestamps/descriptions. Failed HTTP, missing evidence, `UNDELIVERED`, stale delivery scans, and conflicting latest scans cannot become successful delivery.
- All HTTP resource ownership checks precede side effects. Approval identity/time come from the authenticated server user. Model tools cannot grant founder approval/recovery; they cannot submit real orders and must stay within their ToolContext workspace. Tool denial rejects instead of returning a fulfilled blocked object that the dispatcher would label completed.

## Validation and limits

`npm run test:cj-receipt-safety` from `backend` runs 88 tests: 35 provider/authority/receipt regressions, 21 HTTP authorization regressions, and 32 existing CJ/order regressions. All passed with no skips in the isolated offline run. HTTP responses were in-memory fixtures; all real network transports were blocked. An earlier 24-test receipt regression pack run against the unmodified baseline passed 1 and failed 23. The final pack adds explicit authority/model-scope/contradictory-tracking cases and tests the now-separated provider adapter without unlocking public services.

The provider adapter requires an explicit transport. Its tests are implementation tests of the parser and request path, not accepted evidence of CJ schema compatibility or real supplier execution. The ledger uncertainty transition and public lock denial are tested separately; post-ack local persistence failure is exercised using the explicitly labeled local mock path. No real order, payment, tracking update, or seller-account mutation was performed.

Independent review: deployment audit agent approved the locked safety/receipt scope and independently reran 56 receipt/route regressions; capability verification agent independently reviewed the audit agent's route changes and reran its 21 tests. Backend TypeScript no-emit checking passed. The final commit receipt must accompany this document; these engineering reviews are not independent Pillow certification.

## Remaining launch prerequisites

1. Establish verified Amazon US seller access and the actual authenticated SP-API path. The inspected Amazon runtime plugin is architecture-only and uncertified.
2. Complete independent Pillow competence/certification, then implement a trusted, scoped, expiring owner-authority receipt. Current canonical commerce locks intentionally prevent live execution.
3. Prove durable admission before outbound creation across process/container loss, provider-side idempotency or reconciliation, and a safe reconciliation procedure for `SUBMISSION_UNKNOWN`. This patch does not assert cross-process exactly-once ordering.
4. Implement and verify CJ order-detail tracking discovery. A genuine order receipt can have no tracking yet; current tracking sync requires a real tracking number and cannot invent one.
5. Verify actual provider response schemas, stock/variant/shipping suitability, amount/currency reconciliation, cancellations, refunds, returns and settlement. Local fixture tests provide no financial evidence.
6. Demonstrate the production Amazon order → approved supplier order → fulfillment → tracking → customer exception/reconciliation loop, within separately accepted authority and limits, before any 24-hour autonomous-commerce claim.
