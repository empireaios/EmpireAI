# Legacy persisted checkpoint capture

`legacy-checkpoint-capture.cjs` exports `captureCheckpoint({ source, destination, sourceCommit })` and `verifyCheckpoint({ directory, manifestSha256 })`. It has no automatic command-line execution, provider access, application import, deployment or restore function. Source and destination must be absolute canonical paths; the destination parent must already exist and destination must not exist. Use a trusted private local destination outside Git. The source commit is caller-supplied provenance, explicitly not independently verified by this tool.

Runtime requirement: standalone Node with built-in `node:sqlite` and `DatabaseSync` read-only support. Intended Linux runtime is the repository's Node 22.23.2; local tests used Node 24.17.0. Availability must be checked before any operational capture; an old runtime without this built-in cannot execute the tool. It never imports running application internals, and a separate Node process cannot access the application's SQL.js memory. No tool upload or production execution has been performed.

Capture opens the source read-only, copies through that same descriptor into a newly reserved mode-0700 directory, fsyncs the mode-0600 database, compares source identity and hashes, and checks the copied SQLite database's integrity. Source mutation, path replacement, unsupported size (over 1 GiB), links and corrupt SQLite cause refusal. No SQLite connection is made to the source. Partial captures remain for diagnosis without a completed manifest; a retry must use a different destination. No automatic deletion or overwrite is performed. A tested 512 MiB-plus sparse SQLite fixture proves the streaming capture accepts the size of the observed old checkpoint; it does not capture RAM or establish a production quiescence boundary.

The caller must retain the returned manifest SHA-256 independently. Verification checks that pinned manifest, exact database bytes and copied database integrity. It does not establish that the input provenance was truthful or that the database reflects current live memory. Every capture explicitly records pending RAM as UNKNOWN, quiescence and complete-live-state as false, no Redis or sidecars captured, and no import authority. A captured database can be a valid old checkpoint even if the running application has substantial newer state in RAM. No claim of zero-loss cutover or final-save success is made.

POSIX directory fsync is attempted and failures propagate. Windows does not offer this same directory durability contract and records directoryFsyncVerified=false. Filesystem/provider snapshots, multi-store consistency, queued work reconciliation, credential handling for a future remote transfer, import/migration and rollback remain separate work. Do not apply this tool to production without the reviewed operational procedure; this change only supplies offline engineering machinery.

The minimal future disk-only protocol is: independently confirm deployed source identity, runtime support, exact source path and adequate destination free space; choose a distinct private destination; run the reviewed standalone capture against the saved database; retain the manifest hash outside the bundle; independently verify the copied bundle; record that pending RAM remains unknown. Do not print database contents or credentials, upload business snapshots to Git, restart the application, replace the source, or equate successful capture with cutover approval. Any failure leaves the original untouched and its incomplete destination retained for diagnosis.

Validation command: `node --test deployment/legacy-checkpoint-capture.test.cjs`. Local Windows Node 24.17.0 passed five tests using real temporary SQLite databases: copy/reopen and source preservation, injected write interruption, concurrent mutation, failed integrity and tamper/link refusal. This does not constitute production capture, actual process-kill testing, Linux fsync verification or a deployment receipt.

Independent review found an additional race: the copied database could change after hashing and before/during its integrity check. Capture and verification now compare its identity and digest again after integrity. Two regression tests replace the copy with another valid SQLite database at that boundary and require refusal. All seven local tests pass. Product path CI requires this suite with all tests passing and zero skips; Linux proof remains pending until that job executes.
